# Read-Only Data Policy & Source Immutability Guarantee

## 1. Executive Summary

The **Multi-Agent AI Data Analyst** system is built around a non-negotiable architectural invariant:
**Source files and connected external company databases are strictly immutable and read-only.**

Under no circumstances does any agent, service, or API endpoint modify, overwrite, truncate, append to, or reformat user-provided datasets or external database tables.

---

## 2. Policy Enforcement for Uploaded Files (CSV / Excel / Parquet)

### 2.1 In-Memory Working Copies
When a dataset is uploaded or selected for analysis:
1. The file is placed into dedicated upload storage (`storage/uploads/`).
2. An initial SHA-256 cryptographic checksum is computed across the file bytes.
3. The dataset is parsed into an in-memory `pandas.DataFrame`.
4. All downstream operations (data cleaning, feature engineering, lag creation, anomaly scoring, predictive inference, aggregations) are executed exclusively on detached in-memory copies or separate working copies.

### 2.2 Re-verification of Immutability
After analytical pipelines execute, the file's SHA-256 checksum and byte length are verified against the initial state:
- Checksum must match 100%.
- File size must remain unchanged.
- Last modified timestamp on the source file is never refreshed by analytical runs.

### 2.3 Separate Output Storage
All generated artifacts:
- Forecast tables
- Flagged anomaly tables
- Cleaned previews
- Downloadable CSVs
- Markdown analytical reports

are stored strictly in a separate directory (`storage/generated_results/`) with unique IDs (e.g. `forecast_store_1_GROCERY_I_20261026_120000_a1b2c3.csv`). They are never saved into or adjacent to the original source file.

---

## 3. Policy Enforcement for External SQL Databases

### 3.1 Strict Statement Whitelisting
Candidate SQL queries generated by the SQL Agent must strictly begin with `SELECT` or `WITH`.

### 3.2 Prohibited Statements and Keywords
The system strictly parses and rejects queries containing any of the following statements or keywords:
- Data manipulation: `INSERT`, `UPDATE`, `DELETE`, `MERGE`, `REPLACE`, `UPSERT`
- Schema manipulation: `CREATE`, `ALTER`, `DROP`, `TRUNCATE`
- Permissions and access: `GRANT`, `REVOKE`
- Transaction management: `COMMIT`, `ROLLBACK`, `SAVEPOINT`
- Administrative / System procedures: `EXEC`, `EXECUTE`, `CALL`, `VACUUM`, `LOCK`
- File export/import: `INTO OUTFILE`, `LOAD_FILE`, `ATTACH`, `DETACH`

### 3.3 Transaction Controls and Connection Modes
- **PostgreSQL**: Queries are wrapped with `SET TRANSACTION READ ONLY`.
- **SQLite**: Connections are opened strictly in read-only mode (`?mode=ro`).
- **Autocommit**: Autocommit is enforced so that no transaction holds open write locks.
- **Timeout & Limits**: Enforced statement timeout (default 15 seconds) and row caps (default 1,000 rows) prevent resource exhaustion.

### 3.4 Multi-Statement and Injection Prevention
- Semicolons separating multiple statements are disallowed and rejected.
- SQL comments hiding malicious statements (`--`, `/* */`) are stripped during pre-execution validation.

---

## 4. Separation of Application Database and External Source Databases

- **Application Database**: Neon PostgreSQL managed via Prisma in Backend 1 stores user chat sessions, messages, execution metadata, and dataset registry records.
- **External Company Databases**: Read-only source databases connected by the user for analytics.
- **Guaranteed Boundary**: Application records, chat history, agent runs, and model outputs are NEVER written to connected company databases.
